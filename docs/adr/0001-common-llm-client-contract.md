# Единый контракт клиентов LLM через LLMResponse и Protocol

## Контекст и постановка проблемы

Эксперимент использует трёх провайдеров LLM: GigaChat (Sber), Yandex Cloud, MWS GPT.
У каждого свой SDK и свой формат ответа:
GigaChat возвращает `ChatCompletion` из `gigachat`,
Yandex и MWS — OpenAI-совместимые `ChatCompletion`.

Прямое использование SDK в коде эксперимента приводит к тому, что
`experiment_runner` вынужден знать о каждом провайдере отдельно,
а данные о токенах, задержке и ошибках теряются или нормализуются по-разному.

## Рассмотренные варианты

1. **Оставить разные интерфейсы, писать `if/else` в раннере.**
   Просто сейчас, но каждый новый провайдер добавляет ветку в раннер.
2. **Единый контракт через `LLMResponse` + `Protocol`.**
   Все клиенты возвращают одну структуру, раннер не знает про SDK.
3. **Фабрика клиентов с общим базовым классом.**
   Требует явного наследования, что не подходит для модулей без классов.

## Итог решения

Выбран вариант 2. В `src/nir_project/base.py` объявлены:

- `@dataclass LLMResponse` — поля `content`, `model_id`, `input_tokens`,
  `output_tokens`, `latency_ms`, `status`, `error`, `raw`.
- `Protocol LLMClient` — контракт с методом `call_model(prompt, model, ...) -> LLMResponse`.

Каждый клиент (`mws_client`, `gigachat_client`, `yandex_client`) реализует
`call_model` и тонкую обёртку `generate`, возвращающую только текст.
Ретраи и замер задержки выполняются внутри `call_model`, чтобы логировать
каждую попытку. Usage берётся из ответа; при отсутствии — `None`, не `0`.

### Последствия

Плюсы:
- `experiment_runner` не знает про SDK провайдеров, только про `LLMClient`.
- Новый провайдер подключается одной записью в словаре `CLIENTS`.
- Ошибки API не превращаются в пустой успешный ответ: `status="error"` и `error=...`.
- `mypy` проверяет, что каждый клиент соответствует контракту.

Минусы:
- Имена полей usage у разных SDK приходится нормализовать вручную
  (у GigaChat SDK поля могут отличаться от OpenAI-совместимых).
- Для провайдеров, у которых SDK не возвращает `model_id`,
  в `LLMResponse.model_id` попадает запрошенный алиас, а не реальный ID.

## Плюсы и минусы вариантов

**Вариант 1 (if/else):** проще сегодня, но `experiment_runner` начнёт расти
линейно с числом провайдеров. Отвергнут.

**Вариант 3 (базовый класс):** требует явного наследования, а клиенты —
это модули с функциями, не классы. Заставил бы оборачивать каждый модуль
в класс ради формальности. Отвергнут.
